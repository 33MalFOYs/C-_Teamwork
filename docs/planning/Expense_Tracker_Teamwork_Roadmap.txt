PERSONAL EXPENSE TRACKER - TEAMWORK ROADMAP

PURPOSE
Work together to build the project in the same four phases as the AI roadmap:
1. Requirements, project setup, and design.
2. OOP, singly linked list, and input validation.
3. MySQL integration and persistent CRUD.
4. Reports, budgets, CSV, testing, and documentation.

This plan is for team members. The AI roadmap provides additional technical
implementation details. Neither roadmap means the application is already built.
Suggested schedule: one phase per week; adjust to your actual deadline.

AGREED PROJECT SCOPE
- C++ CLI for one user and one selected currency.
- Classes/objects, encapsulation, overloaded constructors and methods.
- A manually implemented singly linked list (SLL), not DLL or CLL.
- Expense CRUD: add, view/search, update, and delete.
- MySQL on local MAMP is the permanent store; Workbench manages the database.
- CSV import AND export using C++ file streams demonstrate file I/O.
- Search by ID, category filtering, and inclusive date-range filtering.
- Monthly spending totals, category totals, and monthly budgets.
- GUI is a future improvement, outside these four phases.

SHARED TECHNICAL AGREEMENTS
Agree on these in Phase 1 and write them in the README:
- Use C++17 unless the course or existing project requires another version.
- Expense fields: ID, amount, category, date, description.
- Date format: YYYY-MM-DD, validated as a real calendar date.
- Money: integer cents in C++; DECIMAL(12,2) in MySQL. Use one currency.
- Positive expense amounts; nonnegative budget amounts; validate field lengths
  and numeric ranges. Do not parse monetary values through floating point.
- Constructor overloading: default and parameterized Expense constructors.
- Method overloading: searchExpense(int id) and
  searchExpense(const std::string& category), with appropriate result types.
- ExpenseNode contains an Expense and one next pointer.
- ExpenseList owns its nodes and releases them safely; prevent unsafe copying.
- DatabaseManager owns SQL operations, FileManager owns CSV operations, and
  ExpenseTracker coordinates them. Avoid SQL embedded in menu code.
- Startup loads MySQL expenses into the SLL.
- A mutation updates MySQL first, then the SLL only after database success.
- If a committed change cannot be reflected in memory, reload before continuing
  operations that depend on those records. Never report a failed save as success.
- MySQL generates IDs, including IDs for CSV imports.
- Agree on method signatures, ownership of returned records, and error reporting
  before members implement calls into one another's classes.

DATABASE AGREEMENT
Database: expense_tracker
expenses:
  expense_id INT PRIMARY KEY AUTO_INCREMENT
  amount DECIMAL(12,2) NOT NULL
  category VARCHAR(50) NOT NULL
  expense_date DATE NOT NULL
  description VARCHAR(255) NOT NULL
budgets:
  budget_id INT PRIMARY KEY AUTO_INCREMENT
  budget_month INT NOT NULL
  budget_year INT NOT NULL
  budget_amount DECIMAL(12,2) NOT NULL
  UNIQUE (budget_year, budget_month)
Validate month 1-12 and the agreed supported year range in the application.

Each developer may run their own MAMP database using the same schema and sample
data. localhost refers to that member's computer, not another member's server.
Share schema scripts and configuration examples, not passwords or database files.
Inspect the actual MAMP MySQL port, server version, and credentials. Do not assume
them. Workbench and the C++ app connect separately to the same MySQL server.
Choose a connector/API compatible with the server, compiler, and architecture.

TEAM WORKFLOW THROUGHOUT ALL PHASES
1. Keep a shared task board: To do -> In progress -> Review -> Done.
2. Give every task one owner, a reviewer, and a concrete completion check.
3. Use short feature branches, such as feature/sll-search or feature/csv-export.
   Keep main buildable. Do not merge work that breaks the agreed build.
4. Before editing a shared interface or another member's file, coordinate with
   its owner and explain which callers need changes.
5. Make focused commits. Review and integrate small working pieces throughout
   each phase instead of waiting until the final day.
6. At each working session, share: finished work, next task, and blockers.
7. Mid-phase, run an integration check. At phase end, hold a short demonstration
   against the completion gate and record remaining defects.
8. Keep credentials, build output, and local machine settings out of Git.
9. If using AI, review its code, run it, and ensure the responsible member can
   explain it. Follow any course policy for AI assistance and attribution.
10. Before submission, test from a fresh checkout with the documented setup.
